# General Rules

## 破壊的操作の制限

復元不可能な操作を防ぐため、以下の代替コマンドを使用する。

| 禁止コマンド | 代替コマンド | 理由 |
|---|---|---|
| `rm` | `trash` | ゴミ箱に移動し、誤削除からの復元を可能にする |
| `git checkout` | `git switch`（ブランチ切替）/ `git stash`（変更退避） | 変更の暗黙的な破棄を防ぐ |
| `git restore` | `git stash` | 変更を保全した上で復元する |
| `git clean` | `git stash -u` | 未追跡ファイルも含めて退避する |
| `git reset --hard` | `git reset`（`--hard` なし）+ `git stash` | `--hard` なしならワーキングツリーを破壊しない |

## `grilling` / `grill-with-docs` スキル発火時の開発ワークフロー

`grilling` または `grill-with-docs` が発火された場合、以下の 5 フェーズを **一連のシーケンス** として最後まで実行する。各フェーズが完了したら、簡潔な完了報告を行った上で続けて次フェーズを起動する。

| # | フェーズ | ツール | アクション |
|---|---|---|---|
| 1 | 設計詰め＆リサーチ | `grilling` または `grill-with-docs` スキル / context7 MCP（フォールバック: WebSearch / WebFetch） | 設計ツリーをラウンド単位で潰しながら公式ドキュメント・参考実装・論文を収集する。`grill-with-docs` は `domain-modeling` を併走させ、`CONTEXT.md` と `docs/adr/` をインラインで更新する。完了後、続けてフェーズ 2 を起動する |
| 2 | プラン作成 | plan mode | プランファイルを書き起こす。ユーザーがプランを承認した後、続けてフェーズ 3 を起動する |
| 3 | テスト駆動実装 | `tdd` スキル | RED-GREEN-REFACTOR ループを回す。完了後、続けてフェーズ 4 を起動する |
| 4 | リファクタリング | `code-review` スキル | 再利用・品質・効率性を改善する。完了後、続けてフェーズ 5 を起動する |
| 5 | セキュリティレビュー | `security-review` スキル | ブランチ差分をセキュリティ観点でチェックする。完了後、ユーザーに最終報告する |

## 補助スキル

以下はユーザーが明示的に起動するスキルで、Claude 側からは自動発火しない。該当する状況に至ったら利用を提案する。

| スキル | 使いどころ |
|---|---|
| `handoff` | 会話が長くなり別セッションへ引き継ぐとき。引き継ぎドキュメントを OS の一時ディレクトリに出力する（ワークスペースは汚さない） |
| `to-questionnaire` | grilling 中に、ユーザー単独では答えられない論点が出たとき。知識を持つ他者へ非同期で回すための質問票 Markdown を生成する |
| `wait-what` | こちらの説明が伝わらなかったとき。`CONTEXT.md` の用語と Simplified Technical English で言い直す |
| `teach` | 設計・実装の前提となる概念をユーザーが学びたいとき。ディレクトリを学習ワークスペースとして複数セッションにわたり教える |

なお `domain-modeling`（`CONTEXT.md` / ADR の作成・更新）と `writing-for-agents`（スキル・`CLAUDE.md`・`AGENTS.md` の執筆）は自動発火するため、明示的な起動は不要。

## 公式ドキュメントの参照

ライブラリ・フレームワーク・API の仕様に基づいて実装や設定変更を行う際は、記憶に頼らず `context7` MCP（フォールバック: WebSearch / WebFetch）で最新の公式ドキュメントを参照する。
参照した場合は、ライブラリ名・URL などの出典を回答に添える。

## 理由の提示

コードや設定の変更・新規作成・ツール選定・破壊的操作の前には、結果だけでなく根拠を示す。
ユーザーが判断・学習できるよう、以下の観点で **実行前のテキスト出力または end-of-turn summary に 1〜2 文程度** で簡潔に説明すること。

- 実装方針を選択した理由（例: 「X ではなく Y を使う理由は〜」）
- トレードオフがある場合はその比較
- 公式ドキュメントやベストプラクティスに基づく場合はその旨を明記し、`context7` MCP などの出典がある場合はライブラリ名・URL を添える

ただし、以下のような自明な変更には理由の説明は不要：

- typo 修正・フォーマット整形
- 変数名のリネームなど意図が明白な変更
- ユーザーが指示した内容の単純な適用（ただし技術的に懸念がある場合は理由を添えて再確認）
