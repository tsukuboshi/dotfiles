# General Rules

## 破壊的操作の制限

復元不可能な操作を防ぐため、以下の代替コマンドを使用する。

| 禁止コマンド | 代替コマンド | 理由 |
|---|---|---|
| `rm` | `trash` | ゴミ箱に移動し、誤削除からの復元を可能にする |
| `git checkout` | `git switch`（ブランチ切替）/ `git stash`（変更退避） | 変更の暗黙的な破棄を防ぐ |
| `git restore` | `git stash` | 変更を保全した上で復元する |
| `git clean` | `git stash -u` | 未追跡ファイルも含めて退避する |
| `git reset --hard` | `git reset`（`--hard` なし）+ `git stash` | `--hard` なしならワーキングツリーを破壊しない |

## `grilling` / `grill-with-docs` スキル発火時の開発ワークフロー

`grilling` または `grill-with-docs` が発火された場合、以下の 5 フェーズを **一連のシーケンス** として最後まで実行する。各フェーズが完了したら、簡潔な完了報告を行った上で続けて次フェーズを起動する。

| # | フェーズ | ツール | アクション | 完了条件 |
|---|---|---|---|---|
| 1 | 設計詰め＆リサーチ | `grilling` または `grill-with-docs` スキル / `context7` MCP（フォールバック: WebSearch / WebFetch） | 設計ツリーをラウンド単位で潰しながら公式ドキュメント・参考実装・論文を収集する | フロンティアが空になり、ユーザーが共有理解を確認したとき |
| 2 | プラン作成 | plan mode | プランファイルを書き起こす | ユーザーがプランを承認したとき |
| 3 | テスト駆動実装 | `tdd` スキル | RED-GREEN-REFACTOR ループを回す | テストが通り、リファクタまで終えたとき |
| 4 | リファクタリング | `code-review` スキル | 再利用・品質・効率性を改善する | 指摘を潰し切ったとき |
| 5 | セキュリティレビュー | `security-review` スキル | ブランチ差分をセキュリティ観点でチェックする | 全指摘に対処し、ユーザーへ最終報告したとき |

## 補助スキル

以下はユーザーが `/` で起動するスキル。該当する状況に至ったら起動を提案する。

| スキル | 提案するタイミング |
|---|---|
| `handoff` | コンテキストが逼迫し、作業を別セッションへ引き継ぐとき。`/handoff <次セッションの目的>` の形で目的を添えるよう促す |
| `to-questionnaire` | grilling のラウンドで、ユーザー単独では答えられない質問が出たとき |
| `wait-what` | こちらの説明が伝わらなかったとき |
| `teach` | 設計・実装の前提となる概念をユーザーが学びたいとき。起動したディレクトリを学習ワークスペースとして多数のファイルを生成するため、学習用の空ディレクトリで起動するよう促す |

`domain-modeling`（`CONTEXT.md` / ADR の作成・更新）と `writing-for-agents`（スキル・`CLAUDE.md`・`AGENTS.md` の執筆）は自動発火するため、明示的な起動は不要。

## 公式ドキュメントの参照

ライブラリ・フレームワーク・API の仕様に基づいて実装や設定変更を行う際は、記憶に頼らず `context7` MCP（フォールバック: WebSearch / WebFetch）で最新の公式ドキュメントを参照する。
参照した場合は、ライブラリ名・URL などの出典を回答に添える。

## 理由の提示

コードや設定の変更・新規作成・ツール選定・破壊的操作の前には、結果だけでなく根拠を示す。
ユーザーが判断・学習できるよう、以下の観点で **実行前のテキスト出力または end-of-turn summary に 1〜2 文程度** で簡潔に説明すること。

- 実装方針を選択した理由（例: 「X ではなく Y を使う理由は〜」）
- トレードオフがある場合はその比較
- 公式ドキュメントやベストプラクティスに基づく場合はその旨を明記し、`context7` MCP などの出典がある場合はライブラリ名・URL を添える

ただし、以下のような自明な変更には理由の説明は不要：

- typo 修正・フォーマット整形
- 変数名のリネームなど意図が明白な変更
- ユーザーが指示した内容の単純な適用（ただし技術的に懸念がある場合は理由を添えて再確認）
